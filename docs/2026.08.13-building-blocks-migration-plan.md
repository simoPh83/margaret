# Building Blocks Migration Plan

## Context

The current `public.units` table represents commercially leased tenant space rather than physical, visual building blocks.

That model works for tenancy and commercial records, but it is awkward for the desired building visualization.

## Problem

A single row in `units` may represent:

- one floor
- multiple floors, e.g. `Floors 1 to 3`
- combined areas, e.g. `Lower Ground & Ground`
- a whole building
- non-floor/service spaces

This makes it difficult to render a building as a simple 2D stack of floor blocks.

## Desired visualization

The target UI is a simple 2D illustration of a building where:

- each floor is a block
- a floor may be split into side-by-side blocks such as East / West or Front / Rear
- each block shows the tenant if let
- otherwise each block shows status such as under offer or mothballed

## Key conclusion

Do not overload the existing `floor` field in `units` to solve visualization needs.

The current `units` table is commercially oriented.
The visualization needs a spatial/layout-oriented structure.

## Recommended direction

Keep `public.units` as the commercial source of truth.

Introduce a separate physical/display layer for building visualization.

### Proposed tables

#### `building_floor_blocks`

Represents drawable physical blocks in a building.

Suggested columns:

- `id bigint generated always as identity primary key`
- `building_id integer not null`
- `floor integer not null`
- `floor_position text not null default 'whole'`
- `display_label text`
- `sort_order integer`
- `created_at timestamp default now()`

#### `unit_floor_blocks`

Maps commercial units to one or more physical display blocks.

Suggested columns:

- `unit_id bigint not null references public.units(id)`
- `floor_block_id bigint not null references public.building_floor_blocks(id)`
- `created_at timestamp default now()`
- primary key on `(unit_id, floor_block_id)`

## Why this model works

It separates:

- commercial reality (`units`)
- physical/renderable reality (`building_floor_blocks`)

This supports cases like:

- one tenant occupying floors 1 to 3
- one floor split into East and West
- ground floor split into Front and Rear
- service spaces that do not behave like normal floors

## Example

A single commercial unit named `Floors 1 to 3` can remain one row in `units`, while mapping to:

- floor 1 / whole
- floor 2 / whole
- floor 3 / whole

The frontend can then render the same tenant name on all three blocks.

## Suggested `floor` convention for visual blocks

- `-1` = lower ground / basement
- `0` = ground
- `1` = first floor
- `2` = second floor
- `3` = third floor

## Suggested `floor_position` values

Use lowercase standardized values such as:

- `whole`
- `east`
- `west`
- `front`
- `rear`
- `centre`
- `service`
- `external`

## Why not just add `floor_position` to `units`

Because many rows in `units` are composite commercial spaces, not single physical display blocks.

Examples:

- `Whole Building`
- `Floors 1 to 3`
- `Lower Ground & Ground`

Those cannot be represented cleanly with one `floor` and one `floor_position`.

## Open design decision

Decide whether the visualization should show:

- current occupancy only, or
- historical/future occupancy as well

This affects whether the mapping table needs date/effective-period fields.

## Recommended next steps

1. Audit current `unit_name` patterns in `public.units`.
2. Classify names into:
   - single-floor units
   - multi-floor units
   - whole-building units
   - service/non-floor units
   - split-floor units such as East / West / Front / Rear
3. Design the physical block schema based on real data.
4. Define mapping rules from commercial units to visual blocks.
5. Only then implement schema changes and backfill data.
