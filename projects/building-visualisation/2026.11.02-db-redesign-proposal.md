# Database Redesign Proposal — Properties, Units and Leases

**Status:** agreed direction, pending implementation
**Date:** 2026-11-02
**Supersedes:** the physical-layer parts of [2026.08.13-building-blocks-migration-plan.md](./2026.08.13-building-blocks-migration-plan.md) (`building_floor_blocks` / `unit_floor_blocks` become `spaces` / `unit_spaces` here)

## Why the current model feels convoluted

The legacy schema uses **attribute-level history** for what is actually **entity-level change**. `units` is a fixed identity with separate timelines hanging off it (`unit_specs_history`, `unit_status`, ...). That works for "the ERV changed" or "status went from vacant to under offer", but a merge or split is not an attribute change — the thing itself stops existing and new things come into being. No attribute update on one row can honestly capture "2nd Floor" becoming "2nd Floor East" + "2nd Floor West".

The redesign therefore versions **entities and their composition**, not attributes.

## Decisions log (from design discussion, 2026-11-02)

1. **Lease amendments exist.** A running lease can gain additional space mid-term (e.g. a storage room added to the demise). When the unit's composition changes, the lease is reassigned to the new unit version from the amendment date. Amendments, merges and splits are modelled as the *same operation* (see below).
2. **Valid-time only.** We track when things were true in the real world (`valid_from` / `valid_to`), not when users happened to enter them. Because the pattern is append-only (history rows are never edited, only closed), `created_by` / `created_at` on every row plus `updated_by` / `updated_at` on temporal tables is sufficient audit. A trigger-based audit log can be added later without changing the model if corrections to closed history ever need tracking.
3. **No stable unit identity.** The backend and frontend will be rewritten, so nothing needs to key off a long-lived `unit_id`. Every version of a unit is a new row; lineage lives in `unit_events`. Consequence: **a unit's composition is immutable for its lifetime** — any change to what a unit contains means closing the row and opening a new one.
4. **Per-space sq ft is always known.** "Rough proportions" is purely a rendering concern (micro-units next to large floors make linear widths unsuitable — use sqrt/log scale or a minimum block width in the frontend). The database just serves honest per-space square footage.

## The three layers

1. **Physical layer** — what the building actually is: buildings → stacks (Radiant House-style frontages) → spaces (a drawable block: floor + position + sq ft). Spaces change only when the building is physically reconfigured; the old row is closed and new rows are opened.
2. **Commercial layer** — what was lettable, and when: a *unit* is a named grouping of physical spaces, valid for a period. Composition lives in `unit_spaces` and never changes for a given unit row. `unit_events` records merges / splits / renames / amendments with parent → child lineage.
3. **Tenancy layer** — leases and statuses as dated facts. A lease never points at a unit directly; it has **dated assignments** (`lease_units`), which is what makes mid-term amendments and merges work without touching the lease's legal terms.

## Schema sketch (PostgreSQL / Supabase)

```sql
-- PHYSICAL LAYER -------------------------------------------------------------

create table buildings (
  id         bigint generated always as identity primary key,
  name       text not null,
  address    text,
  created_at timestamptz not null default now(),
  created_by text
);

create table stacks (
  id          bigint generated always as identity primary key,
  building_id bigint not null references buildings(id),
  label       text not null,               -- 'No. 34', 'Nos. 36-38', '3-4 Bywell Place'
  sort_order  integer not null default 0,
  valid_from  date not null,
  valid_to    date,                        -- null = current
  created_at  timestamptz not null default now(),
  created_by  text
);

create table spaces (
  id         bigint generated always as identity primary key,
  stack_id   bigint not null references stacks(id),
  floor      integer not null,             -- -1 lower ground, 0 ground, 1 first, ...
  position   text not null default 'whole',-- whole|east|west|front|rear|centre|service|external
  label      text,                         -- display label, e.g. 'Ground Floor (Front)'
  sq_ft      numeric(10,2) not null check (sq_ft >= 0),
  valid_from date not null,
  valid_to   date,
  created_at timestamptz not null default now(),
  created_by text,
  updated_at timestamptz,
  updated_by text
);

-- COMMERCIAL LAYER -----------------------------------------------------------

create table units (
  id          bigint generated always as identity primary key,
  building_id bigint not null references buildings(id),
  name        text not null,
  valid_from  date not null,
  valid_to    date,                        -- null = current
  created_at  timestamptz not null default now(),
  created_by  text,
  updated_at  timestamptz,
  updated_by  text
);

-- Immutable composition: no dates here by design.
create table unit_spaces (
  unit_id  bigint not null references units(id),
  space_id bigint not null references spaces(id),
  primary key (unit_id, space_id)
);

create table unit_events (
  id         bigint generated always as identity primary key,
  type       text not null,                -- create|merge|split|rename|amendment|refurb
  event_date date not null,
  notes      text,
  created_at timestamptz not null default now(),
  created_by text
);

create table unit_event_members (
  event_id bigint not null references unit_events(id),
  unit_id  bigint not null references units(id),
  role     text not null,                  -- 'parent' | 'child'
  primary key (event_id, unit_id, role)
);

-- TENANCY LAYER --------------------------------------------------------------

create table tenants (
  id   bigint generated always as identity primary key,
  name text not null
);

create table leases (
  id         bigint generated always as identity primary key,
  tenant_id  bigint not null references tenants(id),
  start_date date not null,
  end_date   date,
  rent_pa    numeric(12,2),
  -- break_date, rent_review_date, etc. as needed
  created_at timestamptz not null default now(),
  created_by text
);

-- Dated assignment of a lease to a unit. A mid-term amendment or merge
-- closes one row and opens another; the lease row itself is untouched.
create table lease_units (
  lease_id   bigint not null references leases(id),
  unit_id    bigint not null references units(id),
  valid_from date not null,
  valid_to   date,
  primary key (lease_id, unit_id, valid_from)
);

create table status_codes (
  code        integer primary key,
  label       text not null,
  short_label text not null,
  color       text not null
);

create table unit_statuses (
  unit_id     bigint not null references units(id),
  status_code integer not null references status_codes(code),
  valid_from  date not null,
  valid_to    date,
  created_at  timestamptz not null default now(),
  created_by  text,
  primary key (unit_id, valid_from)
);
```

### Invariants and integrity notes

- **Uniform as-of predicate.** Every temporal table answers "as of date D" with the same clause:

  ```sql
  valid_from <= date 'D' and (valid_to is null or valid_to > date 'D')
  ```

- **No double-booking of space.** A space may belong to two unit rows only if their valid periods do not overlap. Enforce with a trigger or by materialising `daterange(valid_from, valid_to, '[)')` on `units` plus an exclusion constraint over `unit_spaces`.
- **Derived area.** A unit's sq ft is always `sum(spaces.sq_ft)` over its composition — never stored, so it cannot diverge.
- **Event types.** `amendment` and `merge` are structurally identical (several parents, one child); the type records the *business cause*, not the shape. `rename` has one parent and one child with unchanged composition.
- **Initial load.** Rows created by the original data migration get `valid_from` = the date they were first known; `unit_events` of type `create` are optional for the baseline.

## Worked example — Radiant House (building 415)

Radiant House is the stress test: one `building_id`, three stacks ("No. 34", "Nos. 36–38", "3–4 Bywell Place"), vertically-spanning units, and a ground floor shared by two units. Only the "No. 34" stack is shown below; the other stacks behave identically.

### Initial state (as migrated, 2026-01-01)

Spaces on the "No. 34" stack (sq ft illustrative):

| id | floor | position | label | sq_ft |
| --- | --- | --- | --- | --- |
| S10 | 0 | front | Ground Floor (Front) | 1,100 |
| S11 | 0 | rear | Ground Floor (Rear) | 900 |
| S12 | -1 | whole | Basement | 1,050 |
| S13 | 1 | whole | First Floor | 1,200 |
| S14 | 2 | whole | Second Floor | 1,200 |
| S15 | 3 | whole | Third Floor | 1,150 |
| S16 | 4 | whole | Fourth Floor | 1,150 |
| S17 | -1 | rear | Basement Vault | 180 |

Units and leases:

| unit | name | spaces | sq ft | lease |
| --- | --- | --- | --- | --- |
| U1 | Ground & Basement (34) | S10, S12 | 2,150 | L1: Example Coffee Ltd, 2024-06-01 to 2034-05-31 |
| U2 | Part Ground, First to Fourth Floor (34) | S11, S13-S16 | 4,600 | L2: Example Media Ltd, 2022-03-01 to 2027-02-28 |
| U5 | Basement Vault (34) | S17 | 180 | none (vacant) |

The shared ground floor — the awkward case in the old model — is simply two spaces (S10 front / S11 rear) belonging to different units. Nothing special required.

### Scenario A — split after lease expiry (2027-03-01)

Example Media Ltd vacates; the landlord splits U2 into two lettable units. The physical geometry does not change — **spaces are untouched**, only commercial groupings change.

1. `unit_events`: E1, type `split`, date 2027-03-01. Members: U2 = parent; U3, U4 = children.
2. Close U2: `valid_to = 2027-03-01`.
3. Insert U3 "Part Ground, First & Second Floor (34)" = {S11, S13, S14} (3,300 sq ft), status Vacant from 2027-03-01.
4. Insert U4 "Third & Fourth Floor (34)" = {S15, S16} (2,300 sq ft), status Under Refurbishment 2027-03-01 to 2027-05-31, then Vacant from 2027-06-01.

Children get **explicit initial statuses** — no automatic inheritance; a split is a deliberate business moment and the children's statuses usually differ from the parent's anyway.

### Scenario B — mid-term lease amendment (2027-06-15)

Example Coffee Ltd (lease L1, running until 2034) takes the vacant Basement Vault as extra storage. This is a merge of U1 and U5 driven by a lease amendment.

1. `unit_events`: E2, type `amendment`, date 2027-06-15. Members: U1, U5 = parents; U6 = child.
2. Close U1 and U5: `valid_to = 2027-06-15`.
3. Insert U6 "Ground, Basement & Vault (34)" = {S10, S12, S17} (2,330 sq ft).
4. `lease_units`: close the L1 → U1 assignment at 2027-06-15; open L1 → U6 from 2027-06-15. **L1 itself is untouched** — same tenant, same legal dates, same rent terms (a rent change would be a separate dated fact if needed).
5. U6 gets status Let from 2027-06-15; U1's status timeline ends with the unit.

### Queries the model must answer

Render the "No. 34" stack as of date D (the visualisation query):

```sql
select s.floor, s.position, s.label as space_label, s.sq_ft,
       u.name as unit_name,
       t.name as tenant,
       sc.label as status
from spaces s
join stacks st      on st.id = s.stack_id
left join unit_spaces us on us.space_id = s.id
left join units u   on u.id = us.unit_id
                   and u.valid_from <= date 'D'
                   and (u.valid_to is null or u.valid_to > date 'D')
left join lease_units lu on lu.unit_id = u.id
                   and lu.valid_from <= date 'D'
                   and (lu.valid_to is null or lu.valid_to > date 'D')
left join leases l  on l.id = lu.lease_id
left join tenants t on t.id = l.tenant_id
left join unit_statuses usx on usx.unit_id = u.id
                   and usx.valid_from <= date 'D'
                   and (usx.valid_to is null or usx.valid_to > date 'D')
left join status_codes sc on sc.code = usx.status_code
where st.building_id = 415 and st.label = 'No. 34'
  and s.valid_from <= date 'D'
  and (s.valid_to is null or s.valid_to > date 'D')
order by s.floor desc, s.position;
```

What did lease L1 cover on date D (answers the amendment audit question):

```sql
select sp.label, sp.sq_ft
from lease_units lu
join unit_spaces us on us.unit_id = lu.unit_id
join spaces sp      on sp.id = us.space_id
where lu.lease_id = 'L1'
  and lu.valid_from <= date 'D'
  and (lu.valid_to is null or lu.valid_to > date 'D');
-- D = 2026-06-01 -> Ground Floor (Front) + Basement       (2,150 sq ft)
-- D = 2027-07-01 -> Ground Floor (Front) + Basement + Vault (2,330 sq ft)
```

Where did "Third & Fourth Floor (34)" come from (lineage):

```sql
select p.name as parent_unit, e.type, e.event_date
from unit_event_members c
join unit_event_members p on p.event_id = c.event_id and p.role = 'parent'
join unit_events e        on e.id = c.event_id
where c.unit_id = 'U4' and c.role = 'child';
-- -> Part Ground, First to Fourth Floor (34) | split | 2027-03-01
```

## What the example shows

- **Physical and commercial change are decoupled.** Scenario A changed no spaces at all; scenario B changed no spaces either (the vault already existed as S17) — only groupings and assignments moved. A genuine physical reconfiguration (e.g. splitting floor 2 into East/West) would close S14 and open two new spaces, with units regrouped on top — the same operations once more.
- **Every historical question has one shape of answer.** All three queries above use the identical as-of predicate; there is no per-attribute timeline reassembly.
- **The lease ledger stays clean.** L1's row never changes despite the demise changing — exactly matching the business reality of a lease amendment.

## Open items

1. **Space-level event links.** If we ever need "which spaces did this refurb affect?" as an explicit link rather than inferred from dates, add `unit_event_spaces` — only when a real query demands it.
2. **Rent history.** If rents change mid-lease (reviews, amendment uplifts), add a dated `lease_rents` table rather than mutating `leases.rent_pa`.
3. **Backfill.** Per the old plan: audit current `unit_name` patterns, classify (single-floor / multi-floor / whole-building / service / split-floor), then map to spaces. Per-space sq ft is confirmed always available.
4. **Micro-unit rendering.** Frontend concern only: sqrt/log width scale or minimum block width (cf. the 94 sq ft block at 17-18 Margaret Street).
