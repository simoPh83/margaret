# Building Blocks Migration Plan

## Context

The current `public.units` table represents commercially leased tenant space rather than physical, visual building blocks.

That model works for tenancy and commercial records, but it is awkward for the desired building visualization.

## Problem

A single row in `units` may represent:

- one floor
- multiple floors, e.g. `Floors 1 to 3`
- combined areas, e.g. `Lower Ground & Ground`
- a whole building
- non-floor/service spaces

This makes it difficult to render a building as a simple 2D stack of floor blocks.

## Desired visualization

The target UI is a simple 2D illustration of a building where:

- each floor is a block
- a floor may be split into side-by-side blocks such as East / West or Front / Rear
- each block shows the tenant if let
- otherwise each block shows status such as under offer or mothballed

## Key conclusion

Do not overload the existing `floor` field in `units` to solve visualization needs.

The current `units` table is commercially oriented.
The visualization needs a spatial/layout-oriented structure.

## Recommended direction

Keep `public.units` as the commercial source of truth.

Introduce a separate physical/display layer for building visualization.

### Proposed tables

#### `building_floor_blocks`

Represents drawable physical blocks in a building.

Suggested columns:

- `id bigint generated always as identity primary key`
- `building_id integer not null`
- `floor integer not null`
- `floor_position text not null default 'whole'`
- `display_label text`
- `sort_order integer`
- `created_at timestamp default now()`

#### `unit_floor_blocks`

Maps commercial units to one or more physical display blocks.

Suggested columns:

- `unit_id bigint not null references public.units(id)`
- `floor_block_id bigint not null references public.building_floor_blocks(id)`
- `created_at timestamp default now()`
- primary key on `(unit_id, floor_block_id)`

## Why this model works

It separates:

- commercial reality (`units`)
- physical/renderable reality (`building_floor_blocks`)

This supports cases like:

- one tenant occupying floors 1 to 3
- one floor split into East and West
- ground floor split into Front and Rear
- service spaces that do not behave like normal floors

## Example

A single commercial unit named `Floors 1 to 3` can remain one row in `units`, while mapping to:

- floor 1 / whole
- floor 2 / whole
- floor 3 / whole

The frontend can then render the same tenant name on all three blocks.

## Suggested `floor` convention for visual blocks

- `-1` = lower ground / basement
- `0` = ground
- `1` = first floor
- `2` = second floor
- `3` = third floor

## Status code reference (TODO)

`unit_status.status_code` currently has no lookup table. Observed values are 0–4.
Confirmed so far: `1` = vacant, `2` = let.

Add a `unit_status_codes` reference table (`code integer primary key`, `label text not null`)
to the migration scope and confirm the full mapping (under offer, under refurbishment,
mothballed) before wiring up the UI.

## Findings from drawing prototypes (2026-08-13)

Prototypes rendered for four buildings — 402 (17-18 Margaret Street), 364
(Portland House), 415 (Radiant House) and 392 (Alexandra House). See the
`building-blocks-*.html` files alongside this document.

### Multi-floor commercial units confirmed

Portland House unit 5835 ("Ground Floor & Basement (East) & Basement Vaults",
Futuremaxx, 5,667 sq ft) is one commercial unit occupying two physical floors.
The honest rendering is two blocks — Ground Floor (East) and Basement (East) — with
the tenant name repeated. The DB records only the combined sq ft, so the per-floor
split is a data gap: `building_floor_blocks` likely needs its own `sq_ft` column
(or the split is left to display width heuristics).

### Zero-area service spaces

"Cupboards 2nd–6th Floors" and "Transformer Chamber" (both 0 sq ft) should not be
drawn in the stack. Render them as a footnote/list under the drawing instead.

### Colour scheme

- Tenanted blocks: warm tenant hues (yellow → orange ramp), one shade per tenant,
  consistent within a building.
- Non-let blocks use status colours: vacant = white, under offer = blue,
  under refurbishment = green, mothballed = grey.

### Other observations

- Widths proportional to sq ft work well but need a minimum block width for tiny
  blocks (e.g. 94 sq ft "Fourth Floor (R)" at building 402).
- Unit naming is inconsistent across buildings (`(E)/(W)` vs `(East)/(West)`,
  `(R)` vs `Rear`) — normalise via `display_label` on the physical layer.
- `units.floor` and `units.sq_ft` are null in practice; areas live in
  `unit_specs_history` (latest `effective_from`).

### Multi-frontage buildings (building 415, Radiant House)

Radiant House is one `building_id` covering three physical frontages with
independent floor stacks: No. 34, Nos. 36–38, and 3–4 Bywell Place
(see `building-blocks-415.html`). Implications:

- `building_floor_blocks` needs a stack/frontage concept, e.g. a `stack_label`
  text column or a separate `building_stacks` parent table. Floor numbering and
  floor count are local to each stack (Bywell Place has no 3rd/4th floor).
- A floor row can mix a vertically spanning block and a normal block side by side:
  at No. 34, "Part Ground, First to Fourth Floor (34)" (one commercial unit across
  5 floors) shares the ground floor with "Ground & Basement (34)". The
  many-to-many mapping handles this, but rendering order needs care.

### Whole-building lets (building 392, Alexandra House)

Alexandra House has just two units: "Ground Floor & Part Basement" (Burger &
Lobster, 4,430 sq ft) and "First to Fourth Floors" (Exposure Promotions,
10,421 sq ft) — see `building-blocks-392.html`. With per-floor sq ft assumed, the
rendering is six blocks in a single stack, tenant name repeated per block.

Open question: for a tenant occupying several adjacent floors, do we want the name
repeated on every block, or a merged visual treatment (one tall block / bracket)?
Per-block repetition is the safe default — accurate and consistent with the vacant
rendering.

## Building formations change over time

A building's physical layout is not static: a floor that is a single unit today
("2nd Floor") may be split into "2nd East" and "2nd West" after a refurbishment,
and blocks may merge back later. The physical layer must be versioned over time.

Suggested approach, mirroring `unit_specs_history` / `unit_status`:

- `building_floor_blocks` gains `effective_from date` and `effective_to date`
  (null = current), following the existing `units.is_current` convention, or
- a separate `building_floor_block_history` table.

Points to decide:

- Whether `unit_floor_blocks` mappings also need effective dates (a unit's set of
  blocks changes when the building is reconfigured), or whether remapping is a
  destructive admin operation.
- How this interacts with the "current vs historical/future occupancy" open
  question below — a date-aware physical layer would make time-travel rendering
  possible almost for free.
- Tenant names on blocks always come from leases (which are already dated), so
  history there is free; it is the block geometry itself that needs versioning.

## Open design decisions (to pick up later)

1. **Per-block `sq_ft`.** The DB records only combined areas for multi-floor
   units (confirmed systemic across 364, 392, 415). Assumption going forward:
   per-floor sq ft will be known. Schema should carry `sq_ft` on
   `building_floor_blocks` (or on a versioned history table).
2. **Stack concept.** `stack_label` column on `building_floor_blocks` vs a
   `building_stacks` table (needed for Radiant House-style frontages).
3. **Status codes.** Create `unit_status_codes` lookup; confirm 0/3/4 mapping.
4. **Zero-area service spaces.** Not drawn; rendered as notes. Needs a flag or
   convention (e.g. `floor_position = 'service'`) to keep them out of the stack.
5. **Merged visual treatment** for single tenants spanning adjacent floors vs
   repeating the name per block.
6. **Versioning model** for blocks and mappings (see above).
7. **Backfill strategy.** Parse existing `unit_name` strings ("Ground & Basement
   (East)", "Floors 1 to 3") vs manual entry; who provides per-floor sq ft.
8. **Colour ramp scale.** The yellow→orange tenant ramp works up to ~12 tenants;
   beyond that shades get hard to distinguish (mitigation: accent borders or
   text contrast rules).

## Suggested `floor_position` values

Use lowercase standardized values such as:

- `whole`
- `east`
- `west`
- `front`
- `rear`
- `centre`
- `service`
- `external`

## Why not just add `floor_position` to `units`

Because many rows in `units` are composite commercial spaces, not single physical display blocks.

Examples:

- `Whole Building`
- `Floors 1 to 3`
- `Lower Ground & Ground`

Those cannot be represented cleanly with one `floor` and one `floor_position`.

## Open design decision (occupancy scope)

Decide whether the visualization should show:

- current occupancy only, or
- historical/future occupancy as well

This affects whether the mapping table needs date/effective-period fields.
See "Building formations change over time" above — if blocks are versioned with
effective dates, time-travel rendering comes almost for free since leases are
already dated.

## Recommended next steps

1. Audit current `unit_name` patterns in `public.units`.
2. Classify names into:
   - single-floor units
   - multi-floor units
   - whole-building units
   - service/non-floor units
   - split-floor units such as East / West / Front / Rear
3. Design the physical block schema based on real data.
4. Define mapping rules from commercial units to visual blocks.
5. Only then implement schema changes and backfill data.
